# AI エージェントを使った開発プロセス

AI エージェントを開発へ組み込む場合は、実装をすべて任せるのではなく、人間が要件と重要な判断を管理し、AI エージェントが調査、実装、検証を支援する形にします。

実装前の計画承認と、実装時のコンテキストを引き継がない独立レビューを設けると、要件を誤解したまま実装が進むことと、実装者が自身の見落としを発見できないことの両方を抑えられます。

## 基本の流れ

標準的な流れは次のとおりです。

```text
Issue
  -> 調査と計画
  -> 人間による計画承認
  -> 実装と検証
  -> Pull Request
  -> 別セッションによる独立レビュー
  -> 人間による最終確認
  -> マージ
```

修正が必要な場合は、計画承認では調査と計画へ、独立レビューでは実装と検証へ戻ります。実装後の修正が動作へ影響する場合は、関連するテストや対象環境での確認もやり直します。

この流れはすべての変更へ一律に適用するものではありません。変更の影響範囲と失敗時の危険に応じて、計画とレビューの深さを調整します。

## 人間と AI エージェントの役割

人間は、要件、受け入れ可能なリスク、最終判断を担当します。

- 目的と完了条件を確定する。
- 未確定の業務要件やセキュリティ判断を決める。
- 計画の変更範囲と前提を承認する。
- AI エージェントの指摘に根拠があるか判断する。
- マージやリリースなど、外部状態を変更する操作を承認する。

AI エージェントは、リポジトリと実行結果から確認できる作業を担当します。

- 現在の実装、関連するテスト、ドキュメント、運用ルールを調査する。
- 変更対象、実装方法、検証方法、不明点を計画として整理する。
- 承認された範囲で実装し、テストと自己レビューを行う。
- 実行したコマンド、結果、未確認事項、計画との差異を報告する。
- 独立レビューではコードを変更せず、根拠のある問題点を報告する。

AI エージェントは、コードやメタデータから確認できない仕様を推測で確定しません。判断が必要な事項は、実装前または安全に停止できる時点で人間へ戻します。

## 1. Issue で目的と完了条件を定める

Issue には作業内容だけでなく、なぜ変更するのか、何を確認できれば完了なのかを記載します。

最低限、次の情報を含めます。

- 目的
- 要件
- 対象となる利用者や実行条件
- 完了条件
- 対象外
- 既知の制約や不明点

完了条件は、実装方法ではなく観測可能な結果を中心にします。たとえば「新しいクラスを作る」ではなく、「対象ユーザーが必要な操作を実行できる」「権限のないユーザーは実行できない」のように記載します。

AI エージェントに Issue の下書きを作らせることはできますが、最終的な要件と完了条件は人間が確定します。

## 2. 実装前に調査と計画を行う

AI エージェントには、最初から実装させず、現在のリポジトリを調査して計画を作らせます。

計画では次を明らかにします。

- 現在の構成と関連する既存実装
- 変更対象ファイルと変更理由
- 実装方法と採用しなかった主な選択肢
- 影響を受ける機能、データ、権限、外部連携
- 必要なテスト、静的解析、対象環境での確認
- deploy、リリース、ロールバックに関する考慮事項
- 前提、不明点、人間の判断が必要な事項

計画は Issue コメントなど、プロジェクトで合意した場所に残します。大規模な機能で長期間参照する場合だけ、プロジェクト所定の計画文書を使用します。

## 3. 人間が計画を承認する

計画承認では、コードの細かな書き方よりも、要件理解と変更範囲を確認します。

- Issue の目的と完了条件を正しく理解しているか。
- 変更範囲が広すぎたり、不足したりしていないか。
- 既存実装を再利用できるか。
- 権限、共有、データ、外部システムへの影響を考慮しているか。
- テストと対象環境での確認が実行可能か。
- deploy とロールバックを含め、変更を安全に取り扱えるか。
- 不明点を推測で確定していないか。

問題がある場合は、実装を始める前に計画を修正します。承認後に重要な前提や変更範囲が変わった場合は、その部分を再度確認します。

## 4. 実装、検証、自己レビューを行う

計画を作成したAIエージェントが、そのまま実装を担当しても構いません。計画と実装を分けることよりも、実装者が対象コードと承認済み計画を確認し、変更範囲を維持することが重要です。

実装後は、変更内容に応じて次を実行します。

- 関連する単体テストと結合テスト
- formatter、lint、静的解析
- metadata や設定ファイルの構文確認
- 対象となる開発環境や検証環境での動作確認
- 変更差分の自己レビュー
- 計画と実装結果の比較

「テストした」という要約だけでなく、実行したコマンド、対象、結果を記録します。環境上の制約などで実行できなかった確認は、成功したものとして扱わず、未確認事項として明示します。

実装結果の報告には、少なくとも次を含めます。

| 項目         | 内容                                               |
| ------------ | -------------------------------------------------- |
| 変更ファイル | 追加、変更、削除したファイル                       |
| 実装内容     | 要件に対して何を実装したか                         |
| 確認結果     | 実行したコマンド、テスト対象、成功・失敗・警告     |
| 環境確認     | 確認した環境と、実際に確認した動作                 |
| 未確認事項   | 実行できなかった確認、残っている前提               |
| 計画との差異 | 計画から変更した内容と理由。差異がない場合はその旨 |

## 5. Pull Request で変更と証拠を共有する

Pull Request は、実装内容だけでなく、Issue の完了条件を満たしたと判断できる情報を共有する場所です。

Pull Request には次を記載します。

- 変更内容と変更理由
- 主な変更ファイルと影響範囲
- Issue や承認済み計画との対応
- テスト、静的解析、対象環境での確認結果
- レビュアーに確認してほしい事項
- 未確認事項と既知の制約
- 必要なdeploy、リリース、ロールバックの情報

実行結果は、件数だけでなく、確認対象と実行条件が分かる形にします。変更後の動作をローカルテストだけでは確認できない場合は、対象環境で確認した事実と、まだ確認していない事実を分けます。

## 6. 別セッションで独立レビューを行う

高リスクな変更では、実装時のコンテキストを引き継がない別セッションを使い、独立レビューを行います。

独立レビューの目的は、組織上の正式な承認者をAIで代替することではなく、実装時の前提や思い込みから距離を置いて差分を確認することです。レビュアーは実装者の説明だけを根拠にせず、Issue、承認済み計画、コード、テスト、実行結果から判断します。

独立レビュアーには次の条件を与えます。

- コードや外部状態を変更しない。
- 問題点を優先度順に報告する。
- 指摘ごとに根拠となるファイルや設定を示す。
- 発生条件と利用者への影響を説明する。
- Issue のどの要件または完了条件に関係するかを示す。
- 推奨対応を示す。
- 根拠を確認できない懸念は、確定した不具合と区別する。

指摘は次のように分類できます。

| 重要度   | 基本的な扱い                                                         |
| -------- | -------------------------------------------------------------------- |
| Critical | 重大なセキュリティ侵害やデータ損失につながる。マージしない。         |
| High     | 主要要件を満たさない、または重大な回帰がある。原則として修正する。   |
| Medium   | 条件付きの不具合や保守性、テスト不足がある。影響を確認して判断する。 |
| Low      | 軽微な改善や将来の保守上の提案。必要なら別 Issue とする。            |

AIによるレビューには誤検知があります。重要度の名前だけで対応を決めず、根拠、発生条件、影響を人間が確認します。根拠が成立しない指摘は対応対象にせず、判断理由を残します。

## 7. 人間が最終確認する

人間は、CIやAIレビューの結果だけでなく、IssueからPull Requestまでの情報を確認して最終判断します。

- Issue の要件と完了条件を満たしている。
- 承認済み計画と実装結果の差異を確認できる。
- 必要なテストと対象環境での確認が完了している。
- Critical、Highなど、マージを妨げる指摘が解消されている。
- 意図しない変更が含まれていない。
- deploy、リリース、ロールバックの手順と責任範囲が明確である。

マージ後に実施する作業がある場合は、Pull Requestの完了と混同せず、対象環境、実行者、承認条件を明確にします。

## 変更リスクに応じて工程を調整する

ファイル種別や変更量だけでなく、権限、データ更新、公開範囲、影響を受ける利用者、失敗時の復旧難易度からリスクを判断します。

| 変更の例                         | 計画承認   | 独立レビュー     |
| -------------------------------- | ---------- | ---------------- |
| 文言、コメント、機械的な整形     | 通常は不要 | 通常は不要       |
| 影響範囲が限定されたUI修正       | 簡潔な計画 | 必要に応じて実施 |
| 業務ロジックやデータ更新         | 実施する   | 推奨             |
| 権限、共有、公開範囲の変更       | 実施する   | 実施する         |
| 認証、外部連携、秘密情報の取扱い | 実施する   | 実施する         |
| データ移行や一括更新             | 実施する   | 実施する         |
| 大規模なリファクタリング         | 実施する   | 実施する         |

小さな変更でも、guest userへ公開される機能、権限昇格につながる処理、大量データを更新する処理などは高リスクになります。反対に、変更ファイルが多くても、生成物の機械的な更新で動作差分がない場合は、別の確認方法が適切なことがあります。

## Salesforce 開発で確認する観点

Salesforce開発では、コードだけでなくorgの設定、権限、データ条件によって動作が変わります。変更内容に応じて次を確認します。

- ガバナ制限、バルク処理、非同期処理
- CRUD、FLS、共有、実行コンテキスト
- Permission Set、Profile、Permission Set Groupへの影響
- Business AccountとPerson Accountなど、組織機能やデータモデルへの依存
- Apex test、LWC Jest、Salesforce Code Analyzer
- metadata間の依存関係とdeploy scope
- 対象orgでの画面、PDF、権限、エラー表示などの動作
- 本番データへの影響とロールバック方法

これらを一律のチェック項目として機械的に適用するのではなく、対象コードの実行コンテキストと変更の影響から、必要な確認を選びます。

## 導入するときの考え方

最初から複数のAIエージェントや複雑な自動化を導入する必要はありません。現在の開発プロセスへ、次の2つを追加するところから始められます。

1. 実装前の計画承認
2. 高リスク変更に対する別セッションの独立レビュー

数回運用して、どの変更で指摘が有効だったか、どの工程が過剰だったかを確認します。判断基準が安定した後で、Issue template、Pull Request template、エージェントルール、CIなどへ必要な部分だけ反映します。

## プロジェクト固有ルールとの関係

このページは、AIエージェントを利用する開発プロセスの一般的な考え方を示します。

実際のブランチ作成、コミット、deploy、push、Pull Request、マージ、リリースの承認条件と実行順序は、各リポジトリの開発ルールと組織操作ルールに従います。一般的な流れとプロジェクト固有ルールが異なる場合は、プロジェクト固有ルールを優先します。
