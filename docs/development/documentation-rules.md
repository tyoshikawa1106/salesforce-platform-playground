# ドキュメント配置ルール

AI エージェントが docs を追加、移動、分割するときは、このルールに従って配置します。

## 基本方針

- AI エージェントが作業中に参照する必要があるルール、手順、確認観点は、実行時に見つけやすい場所へ置く。
- README は概要と案内にとどめ、詳細なルール、手順、判断基準は `docs/` 配下に置く。
- 同じ内容を複数箇所に長く重複させない。重複が必要な場合は要点だけを書き、詳細ページへリンクする。
- 本文、見出し、ファイル名には時系列の記録を固定しない。現在使う判断基準、確認観点、再確認条件を残す。
- 個人情報、秘密情報、org 固有値、会話上の一時的な表現は置かず、必要な判断材料だけに要約する。

## 操作手順の安全性

端末、OS、開発ツール、認証、クラウドサービスの状態を変更する手順は、コピーして実行されることを前提に確認します。

- PATH、環境変数、shell profile、OS設定、認証設定などを永続変更する場合は、対象scopeと変更後も影響が残ることを明記する。
- 既存値を上書き、削除、強制置換するコマンドを標準手順にしない。避けられない場合は、変更前の確認、対象の限定、バックアップまたは復旧方法を同じ手順に記載する。
- ユーザーPATHとMachine PATHを合成したプロセスPATH全体を、どちらか一方の永続PATHへ書き戻さない。
- 永続変更の前に、プロセス内だけで確認できる方法がある場合は、その確認方法を先に案内する。
- OSやツール固有の変更コマンドは、公式ドキュメントで現在の動作、制限、影響範囲を確認する。
- setup手順には、成功確認だけでなく、失敗時の停止条件と、安全に元へ戻す方法または公式の復旧先を記載する。
- `setx PATH` はPATHを切り詰めて永続化する可能性があるため、実行例として記載しない。文書検査では、フェンス、インデント、shell prompt付きのコードブロック内で使用を拒否する。
- Windowsのsetup手順では、既定のwinget sourceに現行パッケージがない製品をwingetの実行例にしない。Salesforce CLIとHeroku CLIは提供元の公式インストーラーを案内し、Pythonのインストール先を固定したPATH例を記載しない。
- パッケージマネージャーで環境全体を一括更新または削除するコマンドを標準手順にしない。先に変更対象を表示し、setupで管理するパッケージへ限定するか、dry-runの結果を確認してから実行する。

## 配置判断

docs を追加、移動、分割するときは、次の順に判定し、先に一致した場所へ置きます。

1. 作業前に一度だけ行う準備なら `docs/setup/` に置く。
2. 作業中に毎回守る開発ルール、確認観点、チェックリストなら `docs/development/` に置く。
3. Salesforce 組織に対する deploy / validate / retrieve / destructive changes / data import / Scratch Org 再現の手順なら `docs/deployment/` に置く。
4. リポジトリ全体の構成、またはリポジトリで開発、管理している機能の現行実装の仕様と仕組みなら `docs/specifications/` に置く。
5. README には、プロジェクト概要、主要な docs への案内、セットアップの最短手順だけを書く。

## 配置の補足

- README には個別 docs の一覧や長いチェックリストを置かず、`docs/index.md` へ案内する。
- 決定済みの実務ルールになった内容は、`docs/development/` または `docs/deployment/` の該当するルール文書へ反映する。元の検討記録は作成時点の内容を維持する。
- 機能仕様の単位、命名、分割、記載内容は [機能仕様書ルール](specification-rules.md) に従う。
- 承認済み要求や業務ルールはその管理元を正とし、現行実装仕様と混在させない。リポジトリ内に要求文書を追加する場合は、管理元、承認方法、現行実装仕様との対応を先に定める。
- 実装予定、承認前の要求、判断過程は機能仕様として固定せず、Issue または `docs/discussions/` に置く。
- Salesforce や開発技術に関する汎用的な説明は `docs/knowledge/` に置く。
- `docs/knowledge/` と `docs/discussions/` は作成時点の記録として保存し、後から判明した変更や最新情報に合わせて更新しない。
- ナレッジまたはディスカッションを新しく作成する場合は、調査または検討を行った時点を本文に記載する。
- ファイル名は日付ではなく、内容を表す slug にする。

## 案内更新

新しい docs を追加、移動、削除した場合は、各カテゴリの `index.md` を経由して `docs/index.md` から辿れる状態にします。
`docs/index.md` はカテゴリ別の `index.md` への入口とし、カテゴリ内の個別文書一覧を重複して掲載しません。

## ディスカッション索引

- `docs/discussions/index.md` の一覧は、Apex 設計、Salesforce メタデータ管理、開発環境・リポジトリ運用など、判断対象の分かるカテゴリで分ける。
- 対象が存在するカテゴリだけ見出しを作り、1つの文書を複数カテゴリへ重複掲載しない。
- 業務領域や製品領域は、文書の内容から確認できる場合だけ使用し、ファイル名から推測して分類しない。
