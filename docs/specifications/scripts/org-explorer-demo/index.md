# 組織エクスプローラーデモデータ作成スクリプト

## 概要

スクラッチ組織に、組織エクスプローラーで使用する合成ロール階層と無効ユーザーを作成します。登録内容は[データ定義](../../../../scripts/setup/plans/org-explorer-demo.json)を正とし、組織固有のIDを保持しません。

## 目的・利用場面

スクラッチ組織を作り直した後に、部署、役職、上司、所属ロール、連絡先を同じ内容で再現します。単独実行に加え、Scratch Org準備処理では標準テストデータの投入成功後に呼び出します。

## 対象実装・メタデータ

- [実行入口](../../../../scripts/setup/seed-org-explorer.js)：引数、対象組織、確認入力、実行、照合、一時ファイル削除。
- [定義検証と合成](../../../../scripts/setup/internal/org-explorer-demo.js)：階層検証、要求生成、保存後の照合。
- [データ定義](../../../../scripts/setup/plans/org-explorer-demo.json)：ロール識別名・旧API名・表示名・親、ユーザー項目・所属・上司、標準プロファイル候補、言語設定。
- [匿名Apex断片](../../../../scripts/apex/test-data/seed-org-explorer.apexpart)：不足するロールとユーザーの作成。
- [Nodeテスト](../../../../scripts/setup/test/org-explorer-demo.node.js)：不正定義、対象組織、照合、失敗時の後始末。

新しいSalesforceメタデータや権限セットは追加しません。

## 入力

```sh
npm run setup:org-explorer -- --dry-run
npm run setup:org-explorer
npm run setup:org-explorer -- --verify
```

単独実行の対象組織はSalesforce CLIの`target-org`設定から取得し、設定値は変更しません。Scratch Org準備処理からは作成済み組織の確認済みユーザーを内部的に引き継ぎます。接続先を引数で指定することはできません。未設定や取得失敗の場合は停止します。`--dry-run`は組織へ接続せず、定義と合成予定を検証します。`--verify`は保存済みデータを読み取り、定義と照合するだけです。この2つは同時指定できません。通常の投入では接続組織を表示し、`y`または`Y`で確認した場合だけDMLを実行します。確認を省略するオプションは設けません。

## 処理内容

新規ユーザーには、定義ファイルに記載した`DEMO-`で始まる重複しない架空の従業員番号を設定します。既存ユーザーは従業員番号が未設定でも更新せず、保存前の値を維持します。

ローカルで定義の版、項目、件数範囲、識別子、重複、所属、親・上司の参照漏れと循環、架空電話番号を検証します。ロールとユーザーを親・上司が先になる順へ整えます。ユーザー定義は最大500件とし、50件ずつ上司が先になる順に分割して直列実行します。すべての合成Apexが32KiB以内であることを投入前に検証します。各要求には全対象の識別メールキーを渡し、別の分割で作成したユーザーも管理対象として照合します。

認証済み組織一覧から`target-org`に一致する組織を一意に特定し、Scratch Orgである場合だけ進みます。本番、Sandbox、通常のDeveloper Editionは、確認入力やデータ照会より前に拒否します。組織種別を確定できない場合も停止します。実際の接続先から取得した組織IDを匿名Apex内でも照合します。日本語を含む入力をJSON・Base64として渡し、Apexコードへ直接埋め込みません。

ロールは定義に列挙した`DeveloperName`と移行用の`previousKey`に一致する対象、ユーザーは`Email`が`orgexplorer.seed.<数字>@example.com`の対象を扱います。対象範囲に定義外のレコード、同じメールの重複、有効なユーザー、異なるプロファイル、対象外ユーザーの所属または対象外の子ロールがあれば停止します。

ロールのAPI名は会社・部署・課を表す英語名とし、共通プレフィックスや部署番号を付けません。`previousKey`は旧API名から既存ロールを特定する移行用の値です。新旧API名の両方が存在する場合や、同じAPI名が定義の会社ツリー外に存在する場合は停止します。旧API名で存在するロールも既存データとしてスキップし、IDとAPI名を維持します。

ロールは親から階層単位で不足分だけを作成します。ユーザーも不足分だけを無効状態で作成します。全IDの確定後、今回作成したユーザーだけに上司を設定します。既存のロールとユーザーは識別名・メールで判定してスキップし、名称、項目、所属、上司関係を更新しません。再実行では重複作成せず、全件が存在する場合はDMLを実行しません。

通常実行では保存前後を照会し、新規データは定義した全項目、設定、所属、上司、親ロール、プロファイル、件数を照合します。スキップした既存データは定義との差を許容し、保存前後で変更されていないことを確認します。`--verify`単独では従来どおり全件を定義と厳密に照合するため、手動変更した既存データとの差も検知します。一時Apexは成功・失敗のどちらでも削除します。

## 出力・更新対象

標準`UserRole`の名称と親、標準`User`の氏名、別名、メール、部署、役職、電話、モバイル、言語・タイムゾーン、所属ロール、上司を設定します。新規ユーザーのUsernameには組織IDを含め、組織間の重複を防ぎます。既存データは上司関係も含めてすべて変更しません。部署名はDepartmentに設定し、Titleは「代表取締役」「部長」「課長」「担当」の役職名だけとします。部署・課の所属名をTitleへ重複させません。

結果には作成・スキップ件数と照合結果を表示します。氏名などのデータ内容は集計ログへ出しません。法人営業課の末端ロール（API名 `CorporateSalesStaff`）へ担当ユーザーをまとめ、複数ページと末尾の端数ページの確認に使用します。追加ユーザーの部署と上司も法人営業課に合わせます。営業部ロールには部長だけを割り当てます。合成した氏名、example.comの識別メール、架空連絡先を使用します。登録件数と登録項目の値はデータ定義を参照してください。

## 権限・実行条件

既存の認証でSalesforce CLIを実行でき、UserとUserRoleの作成・更新、関連項目の参照が可能な管理ユーザーを使用します。標準ユーザープロファイルは日本語・英語の候補名とSalesforceライセンスで一意に取得します。別ライセンスや管理者プロファイルへの自動代替は行いません。

## エラー処理

不正な引数・定義、Scratch以外の組織、曖昧な組織、プロファイル不足、対象の衝突、CLI・Apexの失敗、照合不一致では終了コード1を返します。成功、help、dry-run、利用者の取消は0です。

各分割のDMLは1回の匿名Apexトランザクションで行い、その要求内の部分成功は許可しません。後続の要求が失敗しても、完了済みの要求は取り消されません。原因を解消して再実行すると、作成済みデータをスキップして不足分から再開します。通信断やCLIの時間切れではサーバーの完了状態を断定できないため、再実行前に`--verify`と組織の実データを確認します。保存後の照合失敗は保存済み変更を自動では取り消しません。原因を確認し、定義と既存データを照合してから再実行します。

## テスト・確認観点

Nodeテストで不正な階層、対象外のメール・電話、未知の項目、誤った組織、取消、CLI失敗、一時ファイル削除、保存値・関係の不一致を確認します。スクラッチ組織では新規・一部不足・再実行を確認し、新規データの項目と親・上司関係、既存データの不変性、全件存在時にDMLがないことを確認します。

## 制約・注意事項

スクラッチ組織専用です。Scratch Org準備処理では作成済み組織を内部で引き継ぎ、種別を再確認してから専用の作成確認を表示します。通常の`setup:data`への自動追加は行いません。デモユーザーはすべて無効であり、ログインや有効ユーザーのライセンス消費を伴う動作確認には使用できません。電話番号はデータ定義にある架空用途の番号範囲を使用します。

Userは削除できないため、データ定義からの削除を既存ユーザーの削除へ変換しません。作成したデータ全体が不要になった場合は、使い捨てのスクラッチ組織自体を破棄します。ロール数などの組織制限に達した場合も、既存の別データを削除して空きを作る処理は行いません。

## 既知の差異・確認事項

特定のカスタム検証やUser自動化が追加された組織では、その制約によって停止する場合があります。定義は合成データであり、実在する会社・個人の情報を参照しません。
