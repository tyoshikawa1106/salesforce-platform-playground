# 取引先一括更新

## 機能の用途

法人取引先を検索し、一覧の各行で所有者・業種・種別・評価を編集してまとめて保存するLWCです。「Salesforce」アプリの「取引先一括更新」タブから利用します。ナビゲーションの末尾に「取引先一括更新 → 取引先一括削除 → テストデータ一括削除」の順に配置します。

該当なしの案内は、検索または保存後の再取得で0件を確認し、画面に保存失敗行も残っていない場合に表示します。

複数の取引先へ、それぞれ異なる値を入力して一度に保存します。未保存の変更は画面内だけで保持し、行の背景色と「変更あり」で示します。

### 権限・実行条件

- 利用ユーザーに `LwcAccountMassUpdate` 権限セットを割り当て、タブ表示と [AccountMassUpdateController](../../../../force-app/main/default/classes/AccountMassUpdateController.cls) の実行権限を付与します。メタデータのデプロイだけではユーザーへの割り当ては行われません。
- 「Salesforce」アプリへのアクセスも必要です。`SalesforceApplicationUser` はアプリへのアクセスを提供しますが、一括更新専用の `LwcAccountMassUpdate` の代わりにはなりません。
- `LwcAccountMassUpdate` は取引先の参照・編集、業種・種別・評価の項目参照・編集、およびレコード移転権限（`TransferAnyEntity`）を付与します。対象レコードの編集と所有者変更には、Salesforceの共有と所有者移転条件が適用されます。
- Apexは `with sharing` と、検索・DMLの `USER_MODE` を使用します。
- 一覧に必要な項目を参照できない場合は検索が失敗します。編集権限のない項目は画面で無効にします。
- 所有者候補の検索は標準 `lightning-record-picker` と利用者の参照権限に従います。

### 法人取引先の一括更新の利用条件

- 取引先の更新権限、変更項目の権限、共有、所有者移転権限を適用します。
- 個人取引先のIDを直接送信しても更新対象にしません。
- 所有者候補は有効なユーザーです。候補として表示されても、実際の移転可否は保存時にSalesforceが判定します。

### 法人取引先の検索・ページ移動の利用条件

利用者の共有と項目参照権限を適用します。個人取引先機能が有効な組織では `IsPersonAccount = false` に限定し、未有効の組織では通常の取引先を対象にします。

レコードタイプ項目がない組織では、その項目を検索対象に含めません。選択リストは行のレコードタイプごとに取得し、未指定の行ではMasterを使います。取得に失敗した項目の編集は無効にし、再検索を案内します。検索が成功した時点で失敗したレコードタイプだけを再取得し、成功済みの選択肢は再利用します。同じ検索内で失敗した取得を自動的に繰り返しません。

## アクセスするデータ・項目

追加条件がない場合の一覧クエリです。レコードタイプを使用する組織では取得項目に `RecordTypeId` を加えます。個人取引先が有効な場合は法人に限定し、指定された名前・作成日・ページ境界を検索条件に加えます。

```sql
SELECT Id, Name, OwnerId, Industry, Type, Rating, CreatedDate, LastModifiedDate
FROM Account WHERE Id != null
ORDER BY CreatedDate DESC, Id DESC LIMIT 201
```

`Account` の `OwnerId`、`Industry`、`Type`、`Rating` だけを更新します。個人取引先は検索・保存ともに対象外です。新規レコード、保存履歴、非同期ジョブは作成しません。

### クエリの組み立て

取得項目や検索条件を指定する実装は、[AccountMassUpdateSelector.cls](../../../../force-app/main/default/classes/AccountMassUpdateSelector.cls)で確認できます。

### 法人取引先の一括更新の対象データ

成功した行ID、行ごとのエラーを返します。項目に変更がない行はDMLを実行せず完了扱いにします。失敗行の背景色は残り、成功行は解除されます。

### 法人取引先の検索・ページ移動の対象データ

検索結果、現在ページ番号、次ページの有無を返します。この処理ではレコードを変更しません。

## 操作

法人取引先を検索し、変更する行の項目を編集して保存します。

- 取引先名と作成日の開始日・終了日。
- 各行の所有者、業種、種別、評価。
- 検索、ページ移動、変更を保存、変更を取り消す操作。

### 法人取引先の一括更新の操作

- 各取引先の変更された項目と値。
- 検索時点の最終更新日時。
- 保存または取消の操作。

更新対象は所有者・業種・種別・評価だけです。業種・種別・評価は「-- なし --」で値を空欄にでき、所有者はクリアできません。

業種・種別・評価の候補は、既存取引先のレコードタイプに対応するUI APIの選択肢を使用します。`RecordTypeId`が空、またはレコードタイプ未対応で項目が返らない場合はMasterを使用し、利用者の新規作成時の既定レコードタイプで代替しません。

### 法人取引先の検索・ページ移動の操作

| 条件       | 解釈                                                      |
| ---------- | --------------------------------------------------------- |
| 取引先名   | 前後空白を除いた部分一致。`%` と `_` は通常文字として検索 |
| 開始日のみ | 利用者のタイムゾーンでその日の午前零時以降                |
| 終了日のみ | 利用者のタイムゾーンで翌日の午前零時未満                  |
| 両方       | 両端の日を含む範囲                                        |
| 日付未指定 | 作成日による制限なし                                      |

条件はANDで結合します。

## エラー判定

ページ移動後に表示できる行がなくなった場合は、そのページが空であることを表示し、前のページへ戻れます。

操作・取得処理と子部品の例外は各LWCのControllerで捕捉し、同じバンドルのLogicで診断情報を生成してHTML内に処理場所・種類を表示します。既存の業務エラーと操作可否は維持します。診断ログはエラー時だけ生成します。

検索全体のエラーと行別の保存エラーを区別します。保存成功後の再取得失敗では、成功した変更を未保存へ戻しません。詳細は各処理の仕様を参照してください。

### 法人取引先の一括更新のエラー

- 件数・項目・要求形式の不正は要求全体を拒否します。
- 同時編集やレコード取得不能は行単位で拒否し、他の有効な行は保存します。
- DML失敗はステータスコードと確認事項を表示し、内部例外の詳細は公開しません。
- 想定外の例外ではトランザクションをロールバックします。
- 保存応答が不明な場合は入力を保持し、再検索で現在値を確認するよう案内します。
- 保存後の再取得が失敗しても、成功した変更を再送しません。古い値で再編集させないため成功行を一時的に一覧から除き、再検索を案内します。

### 法人取引先の検索・ページ移動のエラー

- 開始日が終了日より後なら検索を実行しません。
- 権限不足や検索例外は画面に表示し、現在の編集内容を保持します。
- 選択肢の読込中は検索・ページ移動・保存を無効にし、別ページへの応答混入を防ぎます。

## 処理詳細

1. [検索・ページ移動](#法人取引先の検索ページ移動)で法人取引先を表示します。
2. 項目の編集値を元の値と比較し、変更がある行を表示します。
3. [一括更新](#法人取引先の一括更新)で変更行だけを保存し、行ごとの結果を反映します。

### 法人取引先の一括更新

現在のページで変更した行を、一回のApex要求でまとめて保存します。

1. 元の値との差分だけを画面内に保持します。元の値に戻した項目は差分から除外します。
2. 変更のある行を背景色と「変更あり」で示し、未保存の変更件数を表示します。
3. 保存では最大200件、重複ID、更新前情報、許可項目と権限をApex側で検証します。
4. 対象をロックして再取得し、最終更新日時が検索時点と違う行や取得不能の行を除外します。
5. 実際に変更された項目だけを `Database.update(..., false, AccessLevel.USER_MODE)` で保存します。
6. 成功行は未保存の変更から除外し、失敗行は入力とエラーを保持します。
7. 標準画面のキャッシュへ通知し、一覧を再取得します。失敗行では元のバージョンを維持し、再保存だけで競合を迂回できないようにします。

「変更を取り消す」は未保存の変更をすべて破棄します。保存済みの変更を取り消す操作ではありません。

### 法人取引先の検索・ページ移動

名前と作成日で法人取引先を絞り込み、作成日時の新しい順に表示します。

再検索・ページ移動の確認中または検索結果の待機中に画面を離れた場合は、元のページと未保存の変更を維持します。再接続後は新しい操作だけが一覧を更新します。

1. 初期表示では検索せず、「検索」で取得します。
2. 作成日時の降順、同じ日時ではIDの降順に並べます。
3. 1ページは最大200件に固定します。次ページ判定用に追加一行を取得します。
4. 次ページは前ページ末尾の作成日時とIDから取得します。前ページの境界を画面内で保持し、「前へ」で再取得します。
5. ページ移動には実行済みの検索条件を使います。入力中の条件は再検索まで反映しません。
6. 未保存の変更がある場合は、再検索・ページ移動前に破棄を確認します。取消または取得失敗なら元の結果と変更を保持します。

一覧の表示項目は取引先名、所有者、業種、種別、評価、作成日時、最終更新日時、変更状態・エラーです。取引先名のリンクは標準詳細画面を別タブで開きます。

### 法人取引先の一括更新の制約・注意事項

選択行へ同じ値を一括入力する補助機能や、ページをまたぐ未保存の変更の保持はありません。保存時には既存の自動化とガバナ制限が適用されます。

### 法人取引先の検索・ページ移動の制約・注意事項

検索結果全体のスナップショットは保持しません。他の利用者の作成・削除・権限変更があると、再取得するページの内容が変わることがあります。総件数や総ページ数は表示しません。保存後も元のページ境界と次ページへの移動可否を保持します。参照できる行が減ると現在ページの表示件数が減り、その後のページ取得がゼロ件になる場合があります。

### 法人取引先の一括更新の既知の差異・確認事項

未確認：所有者変更に伴う関連レコードへの標準動作と、対象組織の入力規則・Flowを含む保存結果は組織上の検証で確認します。

### 法人取引先の検索・ページ移動の既知の差異・確認事項

未確認：異なるタイムゾーンとレコードタイプが混在する実画面の表示は、組織上で確認します。

### 制約・注意事項

ブラウザの再読み込みや画面を閉じる操作では未保存の変更を復元できません。レコードの更新に伴う既存の入力規則、Flow、Trigger、標準の所有者変更処理は適用されます。関連レコードの移転オプションを選択する機能はありません。

### 既知の差異・確認事項

未確認：Chromeでの所有者検索・保存操作は、開発組織へ反映後に確認します。個人取引先が有効な組織での除外分岐は、対応する組織での検証が必要です。
