# テストデータ削除バッチ

## 概要

固定の対象オブジェクトを一つずつBatch Apexで全件削除し、正常終了時だけ次の親オブジェクトへ進みます。

## 目的・利用場面

開発用の投入データを再作成する前に、対象オブジェクトの全レコードを画面から削除します。

## 対象実装・メタデータ

- `TestDataDeleteBatch`: `start`の取得、`execute`の削除、`finish`の停止判定と次バッチ登録。
- `TestDataDeleteBatchService`: 実行条件、削除結果の集計、抽出条件、継続可否の判定。
- `TestDataDeleteBatchSelector`: 実効権限、QueryLocator、残存件数、標準ジョブの検索。
- `TestDataDeleteBatchWrapper`: 固定対象と順序、処理位置、スコープ間集計。

## 入力

画面のControllerが最初の固定計画を渡します。後続は前バッチの`finish`が次の位置を渡します。任意のオブジェクトや任意のSOQLを画面から受け取りません。

## 処理内容

### 対象と順序

正本は`TestDataDeleteBatchWrapper`の`objectNames`です。ファイルと活動を先に処理し、作業指示明細→作業指示→ケース、権利→契約明細→サービス契約、注文明細→注文、商談関連→商談などの順序を守ります。商品・担当者などの参照元を先に削除し、取引先は最後に処理します。

`ContentVersion`の投入データは`ContentDocument`単位で全バージョン・関連共有を含めて削除します。標準価格表本体、営業時間、ユーザー、レポート・ダッシュボードなどのメタデータは対象に含めません。価格表エントリと商品は対象です。

### 非同期処理

1. `start`で環境・実効権限・固定計画・重複を検証し、対象をQueryLocatorで取得する。
2. `execute`で環境・権限を再確認し、ユーザーモードの`Database.delete(..., false)`で分割削除する。
3. `Database.Stateful`でオブジェクト単位の成功・失敗件数と上限付きのエラーコードを保持する。
4. `finish`で標準ジョブの未処理例外、部分失敗、残存件数を確認する。
5. 失敗・残存がなければ次のBatchを登録する。最後の対象を終えたら登録しない。

個人取引先のContactは直接削除できないため、通常のContactを先に削除し、個人取引先に対応するContactはAccount削除に委ねます。アーカイブされた活動も含み、ごみ箱内のレコードは除きます。

## 出力・更新対象

固定対象のレコードを通常削除します。完全削除やごみ箱の空化は行いません。標準の連動削除やTrigger・Flowによる副作用は発生します。途中で成功した削除は後続の失敗でロールバックされません。

オブジェクトごとの標準Apexジョブを生成します。独自の履歴レコードや投入ID台帳は作成しません。

## 権限・実行条件

画面と同じ開発環境・実効権限を、開始時・スコープ処理前・次のバッチ登録前に確認します。全件削除は`Modify All Data`を持つユーザーでユーザーモードの参照・削除として実施します。ファイル処理では`Query All Files`も確認します。

受付時と非同期の開始時に同機能の別ジョブを確認します。同時受付が競合した場合も、競合したジョブを削除前に拒否します。競合時に必ずどちらか一方が成功する保証はありません。

## エラー処理

- スコープ内の個別DML失敗は件数と重複しないエラーコードを集計する。内部メッセージやレコード内容は画面へ転記しない。
- 失敗したスコープでStatefulの値が失われても、`AsyncApexJob.NumberOfErrors`で検知して後続を止める。
- 部分失敗、残存、実行権限喪失は`finish`で停止理由を例外として標準ジョブへ反映する。
- 存在しないoptional objectだけを空処理で通過する。参照・削除権限不足は空処理にせず停止する。
- 中断や開始失敗では後続を起動しない。復旧後は画面で残存を確認して最初から再実行する。既削除のレコードは再取得しない。

## 制約・注意事項

- QueryLocatorで対象を分割し、全件をApexのListへ読み込まない。バッチサイズは起動箇所を正とする。
- 削除中は投入・編集を停止する。対象取得後の追加は残存として検知できるが、検査後の追加までロックする仕組みではない。
- 有効化済み注文、承認ロック、追加されたカスタム参照、自己参照・循環参照、Trigger・Flowの制約などで削除できない場合は停止する。状態や参照を自動変更して制約を迂回しない。
- 対象外オブジェクトも標準の連動削除や自動化の影響を受け得る。全体を一括ロールバックする機能はない。
- `finish`未実行時の独自監視や通知は設けず、標準Apexジョブと画面の残件数で確認する。

## 既知の差異・確認事項

環境判定は削除機能専用です。SandboxではないDeveloper Edition、または`IsSandbox=true`かつ`TrialExpirationDate`が未来のScratch Orgだけを許可します。通常のSandbox、本番、期限切れScratchは拒否します。組織固有の自動化・自己参照・追加参照を含む全件削除の成立は、対象組織の管理者が確認します。
