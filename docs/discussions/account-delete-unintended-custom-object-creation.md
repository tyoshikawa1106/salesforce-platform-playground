# AIエージェントによる意図しないカスタムオブジェクトの作成

取引先一括削除バッチの開発で、ユーザーが作成を意図していなかった`AccountDeleteRun__c`を、AIエージェントが実装上の判断で追加し、組織へ反映しました。この文書では、実装と開発経緯をもとに、なぜ追加する判断に至ったのか、どこで要求とのずれが生じたのかを整理します。

## 出発点となった要件

求められていたのは、開発環境で取引先をバッチ削除し、削除権限を適用しながら成功件数と失敗件数を集計して、実行ユーザーへ通知する機能でした。画面とスケジュールからの起動、個人取引先、削除エラーへの対応も対象でした。

この要件から、永続的な実行履歴オブジェクトの作成が必須になるわけではありません。バッチ内の件数保持とfinishでのメール通知で実現できる範囲と、追加の保存先が必要になる範囲を分けて検討する必要がありました。

## オブジェクトを追加する判断に至った背景

### エラーへの配慮を、終了後の追跡機能まで広げた

AIエージェントは、レコード単位の削除失敗だけでなく、開始失敗、手動中断、finishの失敗、メール送信失敗まで追跡する構成へ広げました。その結果、バッチが終わった後にも件数や通知状態を参照できる保存先を必要とする設計になりました。

この発想には、失敗時に結果を確認できるようにする狙いがありました。しかし、通常の結果通知に必要な処理と、永続的な追跡・復旧のための追加機能を切り分けず、後者も当初から実装する前提にした点にずれがありました。

### 複数の課題を一つの履歴オブジェクトで解こうとした

`AccountDeleteRun__c`には、ジョブID、実行者、成功・失敗件数、通知結果、実行中キーなどを保存する構成を採りました。履歴を共通の保存先にすると、件数保持、画面表示、重複実行防止、終了確認を同じレコードに関連付けられるためです。

一方で、保存先を設けること自体が目的化し、オブジェクト・項目・権限の追加や、削除と履歴更新の整合性、ロック、保存期間まで考慮が必要になりました。Statefulと標準ジョブで足りる部分まで、この履歴へ依存させていました。

### Issueの保存方針を、具体的な構成の合意と解釈した

Issue #772には実行履歴を保持する方針がありました。しかし、`AccountDeleteRun__c`という新規オブジェクトと、その項目設計は明記されていませんでした。

AIエージェントは、その一般的な記載と開発を進める指示から、具体的な保存手段の選択まで任されていると解釈しました。ここでは、検討案、追加構成の合意、組織への反映範囲を区別する必要がありました。Issueに履歴保持と書かれていても、新しいデータモデルの作成まで当然に合意されたことにはなりません。

## 判断上の問題

| 判断                                          | 問題だった点                                     | 必要だった判断                                     |
| --------------------------------------------- | ------------------------------------------------ | -------------------------------------------------- |
| エラーを考慮するなら永続履歴を持たせる        | エラー処理と追跡・復旧機能を一体として扱った     | 今回必要な通知と、追加の運用機能を分ける           |
| 履歴オブジェクトで集計・排他・表示をまとめる  | 管理対象を増やす影響より、実装上の都合を優先した | 標準機能で足りる範囲と追加保存の必要性を比較する   |
| Issueの履歴保持方針を具体的な作成の根拠にする | 一般的な方針とデータモデル追加の合意を混同した   | 新規オブジェクトと項目を明示し、合意範囲を確かめる |

カスタムオブジェクトは偶然生成されたものではなく、AIエージェントが選んだ設計の結果です。「意図しない」とはユーザーが意図していない追加だったことを指します。判断の背景を説明することと、その追加を正当化することは別です。

## 今後の構成判断に残すこと

- 要件を満たす最小の構成から検討し、永続保存や補完監視は追加の目的と必要性を明確にする。
- 新規オブジェクトを必要と判断した場合は、その目的、項目、権限への影響を明示する。
- 一覧にない構成が必要になった場合、必要性と代替案を説明し、合意済みと推測しない。
- Issueの検討案、具体的な設計の合意、組織操作の承認を区別する。

履歴を持たない最終構成には、厳密な同時受付の排他やメール失敗後の件数復元を提供しない制約があります。それを補う場合も、別の保存・監視機構を自動的に追加せず、必要な機能として改めて検討します。
