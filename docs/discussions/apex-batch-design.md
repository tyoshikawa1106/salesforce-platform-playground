# Apexバッチの設計方針

Apexバッチの処理順序、業務処理、検索、定期起動をどのクラスに配置するかを整理します。取引先一括削除バッチを具体例として、初期構成と、その採用をやめて最終構成へ変更した理由をまとめます。

## 設計の前提

基本とする責務は、大量レコードの分割処理、実行条件の確認、結果の集計、完了通知です。これらをBatch Apexのstart・execute・finishの流れで実現できるかを先に検討します。

今回の具体例では、開発環境に限定して、実行ユーザーが参照できる法人・個人取引先を削除権限に従って処理します。バッチサイズは2000件とし、部分的な削除失敗を集計して実行ユーザーへメール通知します。定期起動にも対応します。

2000件というサイズや取引先の削除条件は、この機能の要件です。すべてのApexバッチで共通に採用する値や条件とはしません。

## 最初に追加しようとしたクラス構成

初期構成では、通常の完了通知に加えて、開始失敗、手動中断、finish自身の失敗、通知処理の失敗も補完しようとしていました。そのため、履歴を中心に起動・実行・監視・通知を調整する構成になりました。

以下は、初期実装でバッチの起動・実行・終了処理に関係していたクラスです。名称は当初のものを記載しています。

| クラス                      | 当初の担当                                                           | 対応するテストクラス            |
| --------------------------- | -------------------------------------------------------------------- | ------------------------------- |
| `AccountDeleteBatch`        | startで対象を取得し、executeで削除、finishでMonitorを登録            | `AccountDeleteBatchTest`        |
| `AccountDeleteService`      | 実行条件の判定、削除、集計、履歴保存、終了状態の確定                 | `AccountDeleteServiceTest`      |
| `AccountDeleteSelector`     | 削除対象、実行履歴、標準ジョブの検索と履歴ロック                     | `AccountDeleteSelectorTest`     |
| `AccountDeleteScheduler`    | 定期起動からCoordinatorへ受付を依頼                                  | `AccountDeleteSchedulerTest`    |
| `AccountDeleteCoordinator`  | 履歴作成、バッチと監視の登録、終端確認、通知と排他解除の順序を管理   | `AccountDeleteCoordinatorTest`  |
| `AccountDeleteMonitor`      | Queueableで終端を確認し、失敗時はFinalizerで補完、完了後に監視を解除 | `AccountDeleteMonitorTest`      |
| `AccountDeleteWatchdog`     | 定期監視からMonitorの共通処理を呼び、開始失敗・中断時の終了を確認    | `AccountDeleteWatchdogTest`     |
| `AccountDeleteNotification` | 結果と開始拒否のメール本文生成・送信                                 | `AccountDeleteNotificationTest` |
| `AccountDeleteWrapper`      | 起動受付の結果や拒否理由を受け渡す。Schedulerも利用                  | `AccountDeleteWrapperTest`      |
| `AccountDeleteTestSupport`  | ユーザーや履歴などのテスト準備を共通化する補助クラス                 | テスト専用の補助クラス          |

環境判定には既存の`OrgEnvironment`と`OrgEnvironmentTest`を利用しました。また、この構成はクラス以外に、実行履歴を保存する`AccountDeleteRun__c`と関連項目・権限へ依存していました。

### 当初想定した処理の流れ

1. SchedulerからCoordinatorへ起動を依頼する。
2. Coordinatorが実行条件を確認し、実行中キーを持つ履歴を作成する。
3. Watchdogによる定期監視とBatchを登録し、対応するIDを履歴へ保存する。
4. Batchの各executeで履歴をロックし、Serviceが削除と件数保存を行う。
5. finishではメールを送らず、MonitorのQueueableを登録する。
6. MonitorまたはWatchdogからCoordinatorへ終端確認を依頼する。
7. ジョブの終端を確認して結果を確定し、Notificationで通知して監視を解除する。

Batchには`Database.RaisesPlatformEvents`も指定されていました。未処理例外を`BatchApexErrorEvent`で扱う案もありましたが、上記のクラス構成にイベント購読用のクラスは含まれていません。イベントを発行する指定と、イベントを受け取って集計する仕組みは別です。

## 初期構成の採用をやめた理由

### 通常の完了通知まで追加の非同期処理に依存していた

初期構成は、finish自身の失敗も検出したいという考えから、ジョブの終端状態を確認してから通知する方式でした。しかし、executeで得た結果を通知する目的なら、finishから通知処理を呼び出せます。finish実行中にジョブがCompletedになっていないことだけを理由に、通知を別ジョブへ移す必要はありません。

Monitor、Finalizer、Watchdogを設けると、監視の登録・解除、実行順序、重複通知、監視自身の失敗を扱う必要があります。通常の通知と、finishが実行されない場合の補完を一つの仕組みで解こうとして、処理経路を増やしていました。

今回はfinishで通知し、finish未実行時の補完監視は提供しない構成にしました。

### 調整用クラスの必要性が、追加した仕組みから生まれていた

Coordinatorは、履歴、排他、監視、通知を連携させるために必要になっていました。履歴保存と補完監視を外すと、調整対象そのものが減ります。その状態でCoordinatorを残すと、BatchとServiceの間に処理を渡す段階が増えます。

処理順序はBatch、実行条件と実処理はBatchServiceに置き、Coordinatorは設けないことにしました。

### 通知の独立クラスに、機能をまたぐ共通利用の必要性がなかった

Notificationを分離すると、通知だけを変更・テストしやすくなります。一方、今回の通知はバッチ固有の結果を扱い、他機能から共通利用する要件はありませんでした。

削除、集計、結果通知を一連のバッチ業務としてBatchServiceへまとめることで、結果をどこで生成し通知するかを追いやすくしました。通知を扱うという理由だけで、独立クラスを必須にはしません。

### 件数保持に必要な範囲を超えて永続保存を導入していた

履歴オブジェクトには、件数の永続保存、通知失敗後の確認、排他制御に利用できる利点があります。しかし、バッチ内で集計して完了通知する目的には、Statefulによる状態保持を利用できます。

新規オブジェクトの作成は合意されておらず、項目・権限・保存期間・履歴更新の整合性まで管理対象を増やしていました。今回は永続履歴を設けず、バッチ内に集計状態を保持する構成にしました。

### テストの都合で本体の構成を増やしていた

専用のTestSupportや、privateなServiceを`@TestVisible`で差し替える方式は、テスト準備を簡単にするためのものでした。ただし、構成一覧にない補助クラスを追加したり、テストを内部フィールドへ依存させたりする必要はありません。

既存のTestDataFactoryと各テストクラス内の準備を使い、実行ユーザーや権限、データを用意して公開入口を検証する方式にしました。

## 最終的なバッチのクラス構成

| クラス                        | 担当                                                                 | 対応するテストクラス              |
| ----------------------------- | -------------------------------------------------------------------- | --------------------------------- |
| `AccountDeleteBatch`          | バッチ受付、start・execute・finishの処理順序、Statefulによる状態保持 | `AccountDeleteBatchTest`          |
| `AccountDeleteBatchService`   | 実行条件の判定、削除、集計、結果通知                                 | `AccountDeleteBatchServiceTest`   |
| `AccountDeleteBatchSelector`  | 削除対象と標準ジョブの検索                                           | `AccountDeleteBatchSelectorTest`  |
| `AccountDeleteBatchScheduler` | 定期起動からBatchへ起動を依頼                                        | `AccountDeleteBatchSchedulerTest` |
| `OrgEnvironment`              | 既存の組織種別判定                                                   | `OrgEnvironmentTest`              |

基本の命名は`機能名Batch`、`機能名BatchService`、`機能名BatchSelector`、`機能名BatchScheduler`とします。定期起動を担当するクラスには`Schedule`ではなく`Scheduler`を使います。文字数は`Test`接尾辞まで含めて確認し、長くなる場合は機能名も含めて調整します。

### 責務の配置

- Batchは処理の順序を組み立てる。startで対象を取得し、executeでServiceに処理を委譲し、finishで結果通知を依頼する。
- BatchServiceは業務処理を担当する。今回の例では権限確認、ユーザーモードでの削除、成功・失敗の集計、メール生成・送信を行う。
- BatchSelectorは検索を担当する。実行条件の判定や削除、通知は行わない。
- BatchSchedulerは定期起動の入口とする。バッチの業務処理を重複実装しない。

集計状態は`Database.Stateful`を実装したBatchが保持します。今回の実装では、Batchが持つBatchServiceのインスタンスに件数と上限付きのエラーコードを保持させています。検索結果や大量のエラー詳細をそのまま蓄積しません。

## 初期構成と最終構成のメリット・デメリット

| 観点                 | 初期構成                                                                             | 最終構成                                                                       |
| -------------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| 処理の追いやすさ     | 役割を細かく分離できる一方、複数の非同期処理とCoordinatorを追う必要がある            | start・execute・finishを中心に、BatchとServiceで処理を追える                   |
| 終了後の結果確認     | 永続履歴から結果を確認できるが、保存先と権限の管理が必要                             | 保存先の管理が不要だが、終了後に件数を保存データから復元できない               |
| finish未実行時の通知 | Watchdogで補完する経路を持てるが、監視自身の管理と失敗対応が必要                     | 監視は不要だが、開始失敗や中断でfinishが動かなければ完了メールを送らない       |
| 同時実行の制御       | 一意キーとロックによる排他を設計できるが、履歴との整合性管理が必要                   | 標準ジョブで登録済みの重複を確認するが、同時受付の厳密な排他は保証しない       |
| 通知の変更           | 独立クラスとして扱えるが、呼び出し経路と管理するクラスが増える                       | BatchService内にまとまるが、通知だけを他機能へ共通利用する構成ではない         |
| 未処理例外の調査     | イベント購読を追加すれば詳細を別経路で記録できるが、遅延・重複・集計順序の設計が必要 | 標準ジョブのエラー情報から未確定の存在を示す。イベントによる詳細収集は行わない |
| テスト準備           | 専用補助クラスで重複を減らせるが、別クラスや内部フィールドへの依存が増える           | 各テストで準備と検証を追いやすいが、一部の準備コードは重複する                 |

## 集計とエラー処理の方針

取引先削除の例では、`Database.delete(records, false, AccessLevel.USER_MODE)`の結果から、成功したAccountを成功一件、失敗したAccountを失敗一件として集計します。一つのAccountに複数エラーがあっても重複計上せず、連動削除された関連レコードは加算しません。

レコード単位の失敗と、未処理例外によるスコープ単位の失敗は区別します。標準ジョブのエラー数をレコード数に換算せず、確定済み件数と未処理・件数未確定の有無を通知します。標準ジョブの完了も、全レコードの処理成功と同義には扱いません。

開始失敗や中断でfinishが呼ばれない場合の補完、メールの自動再送、スコープの自動縮小は今回の構成に含めません。必要になった場合は、それぞれ独立した要件として、追加する処理と運用負担を検討します。

## 構成を追加するときの判断

まずBatch・BatchService・BatchSelector・BatchSchedulerで責務を整理し、別クラスでなければ扱いにくい具体的な理由がある場合に追加を検討します。細かく分けられること自体を、分ける理由にはしません。

監視、永続履歴、通知共通化などは有用な場合がありますが、通常の分割処理と完了通知に常に必要なものではありません。追加する目的、標準機能で代替できる範囲、失敗時の振る舞い、管理対象の増加を確認してから採否を決めます。
